# OSS Ideas

Help YU choose and develop an open-source project worth building: one that
people would choose over what already exists, that has real technical depth,
that YU would use, and that can keep growing. A project needs less novelty
than a paper. A more complete, better measured, or better integrated version
of an existing idea in a growing category can be enough; "在增长品类里拼质量"
is a valid strategy.

## Settle the goal before generating ideas

Ask the deciding questions together and early, as short choices: what the
project is for (community impact, technical depth, daily personal use, a
resume showcase), what form it takes (a framework or a polished product, not a
toy or demo), which directions are in or out, and the time and hardware
available. Criteria that surface one rejection at a time cost many rounds.
Reuse answers already given in the conversation or memory. Do not mine YU's
past sessions for ideas unless asked.

Screen out directions where a large platform will likely ship the feature
itself, audiences too narrow to sustain a community, and directions YU has
paused or rejected. If YU rejects a direction, do not return with variants
of it.

## Offer a few developed ideas

Give 3 to 5 ideas rather than a long menu. For each one, state:

- what users get and who they are;
- the closest existing projects, what they do well, and what they lack;
- what the platforms it plugs into already provide, such as an agent
  harness's built-in policies;
- the technical core that makes it more than glue;
- the risks that could break its core value, and only those;
- a validation step of one or two days, with the result that would stop it.

Research the landscape before writing: repositories, package registries,
vendor documentation, and release notes. Read what a close project does, not
only its tagline.

## Treat similar projects constructively

A small similar repository is context, not a verdict. Develop the fullest
version of the idea and state the meaningful difference: more complete,
higher quality, measured, a new setting or audience, or better integrated.
Call a collision only when a dominant project already covers the core
problem, approach, and main value and no meaningful difference remains. For
deep comparisons, follow the method in research-ideas'
[prior-work assessment](../research-ideas/references/prior-work-assessment.md).

## Answer why the project needs to exist

Before committing, answer YU's question directly: is what already exists
enough? Separate where existing tools and the host platform suffice from
where a user would still need this project. Lead with advantages that can be
measured. An advantage that holds in principle but cannot be shown in a test
belongs in the roadmap, not the headline.

## Validate fast and stop early

This stage is validation, not completeness: "fast validate and iterate,
不要拖沓". Run a narrow spike of one or two days with real components and real
runs, and state the stop condition before starting. If the idea proves too
narrow or its value cannot be shown, stop and report so YU can decide, rather
than pushing on.
